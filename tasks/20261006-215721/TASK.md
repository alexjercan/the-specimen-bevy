## Agent findings (research, not user decisions)

- `Cargo.toml` uses Bevy 0.19.1. `~/personal/nova-protocol/Cargo.toml` uses Bevy 0.19.0 and `bevy_asset_loader` 0.27.0. Check dependency resolution with our exact versions before relying on that pairing. Nova's `crates/nova_assets/src/plugin.rs` owns `LoadingState`s, loads small `BootAssets` before `GameAssets`, has a terminal `Failed` path, and schedules content processing after mandatory assets load. `collections.rs` uses explicit typed asset paths rather than folder collections (Nova notes wasm trouble with folder collections). This game needs one Ready/Failed loading gate, not Nova's mod-processing pipeline. Keep the loader in **our new assets crate**, not in core or the logic plugin.
- Nova loads some GLBs only as readiness gates and later resolves the same paths elsewhere. That indirect coupling is not a model to copy. Use explicit typed handles in an `AssetCollection`, and have the render plugin read them after Ready. Existing example loads `Handle<WorldAsset>` via `modules/{name}.glb#Scene0`, spawns `WorldAssetRoot`, and handles `WorldInstanceReady` to clone per-instance emissive materials (`examples/facility_layout/main.rs:215-346`). Preserve this Bevy 0.19 world-asset path until a proven alternative is tested.

The 16 current `facility_floor1_v2_*.png` captures are the chosen visual baseline. `Plan` includes both cells/edges and render `pieces`/lights. Extract logical structure first rather than treating a GLB or a rendered piece as a collision shape.
- `art/visuals/generated/modules/` currently contains **47** GLBs plus manifest, despite stale prose in `art/visuals/PROVENANCE.md` claiming 46. The frozen `facility.glb` belongs only to the old `facility_gallery` example. `assets/` is currently empty. `flake.nix` packages `assets/` and `credits/`; the examples override the asset root to `art/visuals/generated`.
- Poly Haven `concrete_floor_worn_001` CC0 textures are embedded in five generated modules. `art/visuals/PROVENANCE.md` and `art/visuals/sources/polyhaven/concrete_floor_worn_001/SOURCE.md` have source URLs and hashes; `credits/CREDITS.md` has no entries yet. Quaternius is reference only; do not ship the downloaded MegaKit.
- Controller research found no confirmed Bevy 0.19 drop-in FPS controller that is free of physics-library dependencies. `bevy_ahoy` (Avian3d) and `bevy-tnua` (Avian/Rapier) are candidates if the no-physics-library constraint changes; Rapier's kinematic controller also requires Rapier. For this flat, axis-aligned 2.5 m-grid level, start with a fixed-step, 2D horizontal player footprint and authored walls/doors/prop colliders plus a fixed eye height; avoid stairs, jumping, slopes and full mesh collision in the first slice. Compare a swept circle-vs-box with a swept/axis-separated AABB in a tiny test before locking collision shape. Treat multi-floor traversal as a later design task. Bevy 0.19 has `CursorOptions` for pointer capture; test X11 lock/fallback in the game, not only in a headless test.

It does **not** demonstrate loading a GLB through an observer; our renderer must handle loaded asset state and delayed scene instantiation separately. Current example's `WorldInstanceReady` observer attaches glow only after scene children exist. One scout incorrectly claimed `world_serialization` was absent; direct verification found `bevy_world_serialization` in `Cargo.lock`, reexported as `bevy::world_serialization` by Bevy 0.19.1, and `nix develop -c cargo check --example facility_layout -q` passed. ## Follow-up read-only research (no implementation approval)

- Layout scout confirmed 16 areas, 23 authored openings (15 doors, 8 passages), 36 props and 43 fixtures in `examples/facility_layout/layout.rs`. `moves()` treats the one authored closed EXIT door as passable; existing path tests do not test locked traversal. Keep signage/path authoring separate from gameplay door traversability if paths must still route toward a locked EXIT. The test-only `free()` in `examples/facility_layout/tests/layout.rs` already checks a 0.3 m player footprint against cell edges, door widths and prop bounds, but ignores door state; the authoring validator's 0.2 m wall clearance does not prove whole-floor player clearance.
- Rendering scout checked Bevy 0.19.1 world-asset lifecycle: repeated loads of identical `WorldAsset` paths in the layout example and `FacilityAssets` deduplicate through `AssetServer`; `WorldAssetRoot` spawn queues retry if an asset is not loaded. `WorldInstanceReady` fires after descendants are parented. Hot reload replaces descendant entity IDs, so future gameplay must own identity on logical roots rather than cache scene-child entities.
- Controller scout verified `AabbCast3d::aabb_collision_at` is a native swept AABB-vs-AABB time-of-impact query, but returns only a scalar, not a normal or slide response. `BoundingSphereCast` handles sphere-vs-sphere only; it is **not** a swept circle-vs-box solution. Contact at time zero, tangential movement, door-jamb corner ties and two-wall sliding require small focused proofs. The scout's claim that zero-direction NaNs necessarily cause false negatives is unsupported: Bevy's `RayCast3d::aabb_intersection_at` explicitly handles NaNs in min/max; test edge cases rather than treating it as a known failure. No controller code or collision proof was written.

## Proposed architecture (for owner review; not yet approved)

```text
root game binary/lib -> game_core::AppBuilder + GameAssetsPlugin + GameplayPlugin
gameplay::FacilityPlugin = FacilityLayoutPlugin + FacilityInteractionPlugin
                        + FacilityRenderPlugin (+ focused floor/decor/prop render subplugins)
gameplay::PlayerPlugin = PlayerControllerPlugin + PlayerInteractionPlugin
assets::GameAssetsPlugin -> bevy_asset_loader + Bevy asset handles
FacilityRenderPlugin -> assets::FacilityAssets + logical components
FacilityLayoutPlugin / PlayerControllerPlugin -> no assets crate, no renderer
capture/autopilot -> optional review and integration harness, not runtime dependencies of gameplay
```

- The asset crate owns paths, explicit named `Handle<WorldAsset>` fields (or a validated typed map if derive supports it), and `Loading -> Ready | Failed` state. It does not spawn rooms. Verify `bevy_asset_loader` 0.27 on Bevy 0.19.1 and how `WorldAsset` `#Scene0` typed handles are declared, using one test asset first. Fail visibly on missing mandatory assets; do not hang on an unresolved load. Keep preview camera/capture out of runtime startup.
- Extract `authored()`/`derive()` and topology validation into `gameplay::facility::layout`. The logic plugin spawns a level root with cells/areas, floor footprints, walls, door portals, and typed entities for props and objective sockets. Represent blocked footprints in meters (X/Z), not mesh triangles; a doorway is traversable only when the *logical* door state allows it. Keep a stable mapping between grid coordinates and world positions. `RenderableModule` or typed facility marker components describe appearance but are optional for headless logic.
- Register rendering observers **before** logical spawn. On addition of a logical room/wall/floor/prop marker, attach the corresponding asset scene child and visual light, not a second gameplay collider; keep scene children owned by their logical parent. Resolve handles only after Ready (or defer rendering until Ready), and ensure late spawns, removal/replacement of modules and level teardown do not leave orphaned children or duplicate models. Keep material-glow handling tied to `WorldInstanceReady`; clone per-instance materials before animated emissive writes to avoid global flicker. Split `FacilityRenderPlugin` internals by geometry (floor/walls/doors), decor and objective visuals as complexity grows, not by making every module its own crate.
- Player controller: fixed timestep horizontal move/slide against authored static boxes and door state, use floor footprint for ground validity, keep camera look and cursor capture in windowed systems; no rigid-body world or external physics dependency. Interaction targeting is a separate short-range/line-of-sight check against logical interactables. Hiding, fuses, fuse panel and loot need explicit state/target/result transitions; initial art concepts are **not** working mechanics. Keep gameplay on one flat floor initially; no promise of stairs or dynamic NPC collisions in this slice.
